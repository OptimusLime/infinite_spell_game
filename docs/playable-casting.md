# Playable casting study

The game project consumes the reusable engine `spell-player` package. The game owns `players/casting-study.player.toml`, two authored YAML definitions under `spells/casting-study/`, and four scene documents under `scenes/casting-study-*`. The controls, generic Inventory, separate Equipment, finite cartridge funding, authored revision admission and physical execution remain in shared Rust components.

This is a provisional integration study, not accepted art, balance or the complete game. The actor, targets, projectile shapes, capacities, grid sizes, costs and camera values are explicit test inputs inherited from the engineering proof. The four cel/pixel day/night documents share one canonical configuration and session; they are comparison views, not an approved in-game look-switch mechanic. The fixed actor uses explicit named aim targets. Walking, mouse-ground aiming, world generation and final visual design are separate work.

Open `scenes/casting-study-cel-day.scene.luau` and enter Play. Equip the wand, load amber, select the directed bolt study, choose the front target, then Fire. The configured keys are shown beside the controls. Selection and aiming spend nothing. The bottom total includes each owned physical cartridge once; the loaded source is also shown separately. Depleted sources refuse a cast and can be replaced from Inventory.

To revise a spell, edit and save the configured YAML, open **Authored sources**, preview that spell ID, then explicitly **Admit this revision**. A changed file after preview must be previewed again. Admission changes future casts without refilling the inventory or resetting Equipment, physical bodies or funded receipts. Current scenes and camera views share that finite session. Configuration edits require an explicit new session identity; host restart does not restore a durable full-world save.

The ordinary engine package installer records exact package versions and hashes in `atelico.lock`. Native code is built against this checkout's engine, as required by the current registry workspace contract. Installed legacy Spellcraft examples are dependency samples; this study references only the game-owned definitions named in its player configuration.

The actual game host on port 7890 has been verified through native pointer controls, with [the integration receipt](../proof/playable-casting/receipt.json), [continuous 13-second casting/replacement clip](../proof/playable-casting/finite-casting-1100x800.mp4), [wide game view](../proof/playable-casting/final-live-1600x960.png) and [pixel comparison with readable HUD](../proof/playable-casting/view-pixel-day-1100x800.png). The capture is 390 native frames at 30 fps, with no cuts; the on-screen FPS badge measures draw capacity, not recording speed.

The recorded session started at 80 total. An explicit 20-energy bolt reduced it to 60 and damaged its target. Saving and admitting a 10-energy revision preserved that 60, the equipped wand, loaded cartridge and earlier receipt. Two further bolts depleted amber; another attempt was rejected. Replacing it with blue changed custody without changing the total, then the authored push spent 20. The final total is 20 across two distinct cartridge items, with four receipts allocating 20, 10, 10 and 20. All four comparison documents and the normal Player 0.1.0 → 0.1.1 script update preserved the same process/session and receipts. The committed bolt source is the admitted 10-energy revision; a newly started session therefore begins with that revision.

Both 1600×960 and actual 1100×800 framebuffers were inspected. The pixel comparison initially blurred the HUD; Player 0.1.1 now uses the engine's existing crisp layer. Main controls, Inventory, Equipment and source review stay at full resolution, with working pointer controls. Packages were published only to the existing local registry and installed with normal commands; exact pins are in `atelico.lock`. Explicit `app install <name> --registry` updates an existing pinned copy while the default retains project-local development behavior.

This establishes engineering integration, not aesthetic or game-design acceptance. This historical receipt predates the shared native authoring and lifecycle work subsequently completed in tasks 135 and 138: its YAML was saved externally, and its funded instances could remain recorded as running after physical bodies expired. Those later engineering results do not change this recording or upgrade the preserved game process. The running game has deliberately retained its paid 20-energy session; no restart or durable save migration is implied. No refund or recharge was added. Push displacement was measurable but small under the provisional test values, so this does not establish satisfying game feel. Current presentation comparisons and remaining readability findings are tracked in [the battlefield review](../references/battlefield-review.md).
